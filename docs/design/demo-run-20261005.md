# The demo's gate, refusing one PR and passing another — 2026-10-05

This is the dated source a README rewrite will quote when it says the gate
bites (agentops-hy6o.29). Two
pull requests were opened on the demo repository,
<https://github.com/NightWatchEng/nightgate-demo>. It is a `node:http` slug
service, enrolled on Nightgate v3.0.1
(<https://github.com/NightWatchEng/nightgate>) with the three commands in
Nightgate's README. One PR carries a planted defect and stays open with its
gate red. The other is a small real change, reviewed and attested before it
was opened. Its gate went green and it was merged. The demo's rule
(`.warden/rules/secrets-in-diff.md`), its skills policy and its workflow are
byte-for-byte what `warden init` emitted, and nothing was tuned to produce
either outcome.

Every line in a `text` block below is verbatim. Blank lines are not
kept, and where other lines are left out of the middle of a block, a
`[...]` line marks the place. Where a line came from a local run and not from CI, the text
before the block says so. Run times are the start time rounded to the
minute, UTC.

## What each PR did

**PR A, the refusal.** <https://github.com/NightWatchEng/nightgate-demo/pull/2>
is deliberate, and its title and description say so. It raises the `/slug`
length cap in `src/app.js` from 200 to 2000. That breaks one existing test,
`GET /slug with overlong text is a 400`. It also adds `src/config.js`, which
commits a string shaped like an AWS access key id: `AKIA` followed by 16
uppercase alphanumerics, invented and granting nothing. The gate refused it.
`warden verify --scope node` failed, and the `warden gate` check failed after
it. It stays open and red as the demo's record of a refusal.

**PR B, the clean change.** <https://github.com/NightWatchEng/nightgate-demo/pull/3>
adds `GET /version`. It returns the service's `name` and `version`, read
once from `package.json` at start-up. Two tests cover it, and the README's
endpoint table lists it. It was built the way the demo's
`.warden/skills-policy.md` says: `warden verify --scope node` passed locally
first. It was then reviewed with the skill pack's `pre-pr-review`. That was
one round with the platform's default crew, a finder then a judge, each in
its own context, because the demo declares no `graph.yaml`. The round found
nothing, and the attestation shard was committed on the branch before the
PR opened. The gate passed and the PR was merged with a merge commit, so
the attested head stays in `main`'s history.

## What this record does not show

- The gate's refusal of the key is not in any CI run. On a PR whose tests
  fail, review never runs (PR A, above).
- The gate `warden init` v3.0.1 emits does not check the attestation, and
  the demo runs that gate unmodified. The demo stays at LEVEL 3, and E-01
  is the first reason it is not LEVEL 4. PR B's
  shard is committed and passes `attest check`, but only a local run says
  so.
- In the CI log, the verify step prints only the end of `npm test`'s
  output, so the failing test's name is not in the log. It is in the
  `warden-verify` artifact, which the emitted workflow keeps for one day.
  This record is where the name is kept.
