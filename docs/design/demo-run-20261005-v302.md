# The demo's gate at v3.0.2: one PR refused, two passed — 2026-10-05

This is the dated source a README rewrite will quote when it says the gate
refuses a bad change and passes a good one. It supersedes
`demo-run-20261005.md`, which was made at v3.0.1. Some of what that record
showed came from local runs, because the v3.0.1 gate could not show it in
CI. Everything quoted here comes from CI.

The demo repository is <https://github.com/NightWatchEng/nightgate-demo>, a
`node:http` slug service. It was enrolled on Nightgate v3.0.1
(<https://github.com/NightWatchEng/nightgate>) with the three commands in
Nightgate's README, and was then moved to v3.0.2 the way Nightgate's
Releasing and Installation pages tell an adopter to. The demo's rule
(`.warden/rules/secrets-in-diff.md`) and its skills policy are byte for
byte what `warden init` emitted. Nothing was tuned to produce either
outcome.

Every line in a `text` block below is verbatim, from a CI job log or from a
comment the gate job posted. Blank lines are not kept. Where lines are
left out of a block, at its start, in its middle or at its end, a `[...]`
line marks the place. Run
times are the start time rounded to the minute, UTC.

## What each PR did

**The bump, PR #4.** <https://github.com/NightWatchEng/nightgate-demo/pull/4>
moves `repo.yaml`'s `platform.pin` from `v3.0.1` to `v3.0.2`. Moving the pin
does not rewrite a workflow, so the PR also copies in two pieces of the
workflow `warden init` 3.0.2 writes: the `gate` job and the `warden verify
--scope node` step. They were taken from a scratch repository enrolled with
`warden init` 3.0.2 at the repository root, for node. The new gate job runs
review, the review-tier check, `warden attest check` and `warden certify`
whatever verify said, and only then fails if verify failed. The new verify
step copies the list of failing tests into the job log and the step
summary. The PR was judged by the gate it brings in, so it needed a
committed pre-PR review attestation itself. It got one, its gate passed,
and it was merged.

**The refusal, PR #2.** <https://github.com/NightWatchEng/nightgate-demo/pull/2>
is deliberate, and its title and description say so. It raises the `/slug`
length cap in `src/app.js` from 200 to 2000, which breaks one existing test,
`GET /slug with overlong text is a 400`. It also adds `src/config.js`, which
commits a string shaped like an AWS access key id: `AKIA` followed by 16
uppercase alphanumerics, invented and granting nothing. To run it under the
new gate, `main` was merged into its branch. That merge had a conflict in
`src/app.js`, resolved by keeping both `main`'s `/version` endpoint and the
planted cap. The gate refused the PR on three counts in one run: the
failing test, the key, and the missing attestation. It stays open and red
as the demo's record of a refusal.

**The clean change, PR #5.** <https://github.com/NightWatchEng/nightgate-demo/pull/5>
adds an optional `separator` to `GET /slug`: `-`, the default, or `_`. Any
other value is a 400. The README documents it. It was built the way the
demo's `.warden/skills-policy.md` says, with `warden verify --scope node`
passing locally first, and was then reviewed with the skill pack's
`pre-pr-review`. Because the demo declares no `graph.yaml`, each round used
the platform's default crew: a finder, then a judge, each in its own
context.
- Round 1 confirmed two low-severity findings. `slugify` accepted any
  separator, and a test name claimed more than the test checked.
- A repair commit fixed both, with regression tests.
- Round 2 verified both fixed and attested clean.

Both rounds' shards were committed on the branch. The gate passed, and the
PR was merged with a merge commit, so the attested commits stay in `main`'s
history.

## What this record does not show

- In CI, PR #2's three refusals land in three different places. The
  failing test's name is in the verify job's log and step summary, but the
  sticky comment's verify line does not name it. The HIGH finding is in the
  sticky comment, but not in any step summary: `warden review` writes none,
  and its log line gives only the count. The missing attestation is only in
  the gate job's `pre-PR review attestation` step, its log and its step
  summary. A reader needs the comment, the verify job and the gate job to
  see all three.
- The demo stays at LEVEL 3. Its gate runs no `warden memory ingest` on
  push (E-03), and its corpus holds four review events against the five
  that E-04 needs.
- The demo's workflow differs from what `warden init` 3.0.2 writes in two
  places that the copied job and step do not cover. The demo's header
  comment still describes the 3.0.1 gate. And the 3.0.2 template puts an
  `id: warden` on the verify job's install step, which nothing in that job
  references; the demo's verify job has no such line. The bump PR's review
  round raised the header comment and dismissed it with that reason.
