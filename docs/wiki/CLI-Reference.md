# CLI Reference

Two binaries ship in one package: `warden` (the gate) and `cage` (the
unattended runner's enroller). Consumers invoke warden through the pinned shim
at `.warden/bin/warden` — see [Installation](Installation.md).

## Exit codes

| Code | Means |
|---|---|
| `0` | clean |
| `1` | a blocking finding, or a failed gate |
| `2` | infra or config error — **the gate did not run** |

`2` is never folded into a verdict. A gate that fails open is worse than no
gate, because it produces confidence.

## The commands

| Command | What it does | Evidence |
|---|---|---|
| `init` | enrolls the working directory, which must be inside a git repository: exit 2, writing nothing, outside one. Detects `pyproject.toml`, `package.json` and `go.mod` by file presence, each one enrolling its language, and writes `repo.yaml` (detected verify commands, `platform.pin` at the installed version, `repair.budget`), the catalog's unconditional starter rules for those languages, `.warden/skills-policy.md`, the CI workflow, and appends the derived-state entries to `.gitignore`. The workflow is `.github/workflows/warden.yml` at the git root; below it, in `svc/api`, it is the git root's `.github/workflows/warden-svc-api.yml`, whose jobs run in `svc/api` and whose gate check is `warden gate (svc/api)`, and exit 2 when a folder name on that path is not letters, digits, `.`, `_` or `-`. The workflow reads `platform.pin` from `repo.yaml` when it runs and builds that tag. Exit 1, writing nothing and naming each file, when any file it would write exists; exit 2 when no manifest is in the working directory | the files it writes; no run dir |
| `explain` | orientation brief from `repo.yaml`: components, risk tiers with reasons, protected paths, verify scopes, which rules fire on a diff, and the local hook gate's state | `brief.md` |
| `plan` | task packet for one piece of work: paths, risk tier, must-pass commands, and memory priors for the areas it names. `--path <file>` (repeatable, read relative to the current directory) tiers each named file as `explain --base` tiers a changed one, and refuses a path outside the enrollment — so an enrollment's own gate workflow above it, which `explain` tiers HIGH, is not one it takes; the tier is UNKNOWN only when no hinted path, named path or hints-file `risk` gives one | `task-packet.json/.md` |
| `verify` | runs a `verify:` scope from `repo.yaml`. Deliberately runs on a **dirty** tree — it is mid-iteration tooling — but the flag travels with the result: the artifact records `dirty`, the summary warns, and `audit` pairs the verdict with the same-commit review. Tri-state: when git cannot determine tree state, both surfaces say *not recorded* rather than rendering it clean. Head and tree state are read when the commands start and again when they end: a HEAD whose value or reflog differs between the two records `head_sha: unknown` (so a switch away and back is caught), and a tree dirty at either point records `dirty`; an edit made and undone between the two reads is not seen. The summary line carries pytest's counts, summed over the steps that declare `runner: pytest`, and withholds them, saying why, when a declared step printed no summary or several, or an undeclared step printed one. `--check-head SHA` runs nothing and writes nothing: exit 0, naming the artifact, when the newest result for SHA under the scope is a PASS on SHA itself from a clean tree of the commands `repo.yaml` declares for the scope now, else exit 1 naming why; `.githooks/pre-push` asks it before re-running the suite | `verify-result.json`; none under `--check-head` |
| `take` | `take --from DIR`, in the gate job: replaces `.warden/out` with a fresh directory and copies into it each regular `verify-result.json` found below `DIR` in a directory named `*-verify`, following no symlink; a symlinked result file is skipped. Exit 2 when `.warden` or `DIR` is a symlink or not a directory, when a directory below `DIR` or a candidate result cannot be read (naming the path and the error), or when nothing was taken | `.warden/out/*-verify/verify-result.json` |
| `deploy` | runs a `deploy:` scope through the same runner, behind preconditions checked first: the checkout must **be** the commit, the commit must be reachable from the deploy branch, and its own diff must have introduced a clean committed attestation shard. A refusal runs no command and names every reason; on success the scope's commands run in order and **halt at the first failure** | `deploy-result.json` |
| `review` | the rules gate on a diff. `engine: python` and `engine: declarative` rules block; `engine: claude` rules defer to the pre-PR review. `--base` locally, `--event` in CI. `--no-project-checkers` exits 2 instead of importing `.warden/checkers/` modules, for a job that must run no code from the checkout | `review-findings.json` + the sticky PR comment |
| `diff` | writes the byte-deterministic review package for a range — resolved SHAs, `git log --oneline`, `--stat`, and a `-U10` diff in one file. Review subagents read it from disk instead of inheriting a diff through context | the `-o` file |
| `declare check` | does the gate's behaviour match what it DECLARES? Five named checks, each comparing a declaration to the behaviour it governs: **D-01** every `verify:`/`deploy:` step's reach is declared (`covers:`) rather than narrowed by the `cwd` + `components:` inference; **D-02** every input the gate reads carries a `hashed` claim in warden's own inventory and every claim holds — repo.yaml's subtrees proved by PERTURBATION (change the bytes in a scratch copy, see whether `rules_version` moves), the package surfaces by set-equality against what `rules.py` hashes; **D-03** every declared verify scope runs in the SAME CI job that runs `warden review`, because verify evidence pairs by SHA inside one runner's filesystem, or is TAKEN from a job that job `needs`, the layout `warden init` writes. A take counts only as the one-line `warden take --from` step in the form `warden init` writes, `warden take --from "$RUNNER_TEMP/warden-verify"`: the needed job runs the scope before an `actions/upload-artifact` step whose `path` names `verify-result.json` under the `.warden/out/` of the working directory that step ran in; the gate job downloads that artifact by name to a `${{ runner.temp }}/...` path; and between that download and `warden review` a step runs `warden take --from` on the same path, spelled `$RUNNER_TEMP`, `${RUNNER_TEMP}` or `${{ runner.temp }}`, quoted or not, with nothing else in the step: no `if`, `env`, `working-directory` or `continue-on-error`, and `shell: bash` on the step itself (a job or workflow default is not read); the download sets only `name` and `path` under `with:` (no `run-id`, `repository` or `github-token`), and no other `actions/download-artifact` step can write into that path; the job and the workflow carry no `env`; and the take step's effective working directory, the job's `defaults.run.working-directory` or else the workflow's, is the `warden review` step's, which the subdirectory gate `warden init` writes below the git root satisfies. The step that ran the scope must have run in that same directory too, since review pairs a result by commit and scope name alone: where the verify job's directory and the take and review directory differ, in either direction, the drift names both. Anything else is drift, and the drift names why. A workflow written by `warden init` 2.1.0 has a multi-line take step, which now reads as drift: replace that step with the one-line form. It does not prove that no earlier step shadows `warden` on PATH or runs review in a spelling whose text does not read `warden review`, does not read `if:` on any job or step other than the take step, and does not check that the upload glob matches. It does not read what other steps before review do: one can plant results in the download directory or set `BASH_ENV` through `$GITHUB_ENV` before the take, or rewrite `.warden/out` after it, and `warden review` has the same exposure; **D-04** every path the repo declares as gate surface — `protected_paths`, the policy's Never-edit paragraph — classifies under a `risk_tiers` glob rather than the unmatched LOW default, an explicit `tier: LOW` being a statement and the default not; **D-05** where graph.yaml declares `review.delegation`, the repository's `allow_auto_merge` read through `gh api` is false — REFUSED when true, a verdict whose read answered naming the repository read, which `gh` picks by `GH_REPO`, then `gh repo set-default`, then the remotes (upstream before origin); UNREADABLE when `gh` cannot read it — never clean, and it moves no exit code, as `certify` holds no D-05 rung. Exit 0 clean, 1 drift, 2 a check could not evaluate. `--json` for a machine | stdout only — it reads declarations and writes no run dir |
| `round new` | mints ONE isolated review round and writes the package into it: a directory derived from the UTC microsecond, the branch, the head sha and the pid, created with `exist_ok=False`, holding `review-package.md`, `round.json` and an empty `reviewers/`. Prints the path and nothing else on stdout, so a caller writes `ROUND="$(warden round new --base origin/main)"` and never types a path that could collide. The base is the REMOTE-TRACKING ref: a `--base` that is BEHIND its own upstream is refused (exit 2), because `git fetch` moves only `origin/main` and a round minted against a stale local `main` records a base nobody is reviewing against — which `warden round classify` cannot see from a manifest. A directory that already exists is REFUSED, never reused — a collision is a stop, not a silent read (a foreign branch's package once landed in a builder's round with a MATCHING base sha and read as plausible on every axis anything checked). `round.json` also records WHICH round this is — 1 for the first review of a change, 2 for the next — derived from TWO chains rather than counted a second way, with the HIGHER of them taken. One is the shards COMMITTED in `base..head`: their `reviewers[].round`, counted for every shard file ADDED by a commit on the range's first-parent walk (never by the `sha` a shard names inside itself, which a rebase rewrites, and never by what the head tree happens to hold). That half is the FLOOR — it rides in the range, so a rebase carries it, where the directory count alone returned 2 rounds before a rebase and 1 after and handed a branch at the cap a fresh budget. The other is the round directories under the gitignored `.warden/out/rounds/`, counted by the two ancestry tests `round classify` proves its chain with — a prior round counts when this head is, or descends from, the head that round was minted for AND that head is not already reachable from the base, so a base branch that moved underneath the work does not renumber the change's own rounds, with heads deduped, since two directories minted for one commit are one round re-run. That half can only RAISE the floor, which is what numbers a round whose shard is not committed yet. Every reading behind the number prints on stderr and none is resolved away — the same `notes` that `round count` prints, so a reading added there reaches both surfaces without a second edit: the two counts disagreeing (`disagreement`: naming both, the direction of the gap, and every shard counted); any shard in the range whose roster records no round at all (`unrecorded`); any shard READABLE AT HEAD that no counted commit added and whose bytes the base branch does not carry (`uncounted` — reported and never counted, for the reasons the `round count` row gives); and the `rewrite` report, which a mint can never carry, because it is read off a `--prior-head` and `round new` takes none. A shard deleted later in the range still counts, because the ADD is the key, and its deletion is carried by a commit in the range as a `.warden/memory/**` change that `evidence-intact` is dispatched on; a history rewrite that DROPS the commit which added it leaves the range no memory change at all, and is answered by a witness from outside the branch — `round count --prior-head`, which `round new` does not take, since a mint has no earlier pushed head to name. `warden attest write --review-dir` checks the roster's `round` labels against that number, so which declared crew a roster is measured against stops being the builder's to type. Exit 2 when the range will not resolve, the round cannot be isolated, or the chain cannot be numbered — a round directory whose `round.json` warden cannot read is not a round that is absent — nor is a committed shard in the range that will not read as JSON, is not a JSON object, carries a `reviewers` that is not an array (an explicit `null` included — the key being ABSENT is the legacy shape and the only tolerated one, and the two used to be indistinguishable), carries a `reviewers` that is the EMPTY array (the schema's floor is `minItems: 1`; a roster stated as nobody used to read as the legacy shape and lower the floor), carries an entry that is not an object, or states a `round` in a shape warden does not read (`2.0`, `"2"`, `0`, `true`) — and a round with no number cannot have its roster checked against the declared crew | the round dir |
| `round count` | the round cap, checked where the builder is NOT standing. The count is derivable from the range — the shards COMMITTED in `base..head` carry `reviewers[].round` — and the only caller was `round new`, on the builder's own machine, which left a budget enforced on a laptop. This is the surface anything holding the range can call, and this repo's CI gate job calls it on every PR. Prints the whole reading as JSON on stdout — the range (`base`, `head`); the numbers (`number`, `capped_rounds`, `from_shards`, `from_rounds_dir`, `from_prior_heads`); every shard counted (`shards`, path and round each); the closure shards (`closure`); the shards whose roster records no round (`unrecorded`); each prior head read, with its own shards and closure paths (`prior_heads`); the two chains' `disagreement`; the `rewrite` report; the `uncounted` shards — readable at head, added by no counted commit, and not carried by the base branch's own tree, REPORTED and never part of `capped_rounds`, because the count stays keyed on the ADD and walks first-parent, so a side-branch ADD the change merged in, an ADD made by a merge commit itself (which `git diff-tree` reports no diff for), and a shard re-added at a path the base also carries all read this way, and so does a branch's own honest commit whenever the head counted is a merge ref whose first parent is the base tip; and the cap it was measured against and where that came from (`cap`, `cap_source`) — and every note on stderr, exactly as `round new` prints them — no reading is resolved away. Exit `0` at or under the cap, `1` over it, `2` when the chain, a `--prior-head` or the declared cap cannot be read. WHICH WAY IT ERRS, because a round counter errs in both: a HIGHER count buys a later round's smaller declared crew, a LOWER one buys repair budget. What it gates on is `capped_rounds` — the highest round a NON-closure committed shard records, ANYWHERE the count looked: the range AND every `--prior-head`. That is a FLOOR off evidence the branch itself committed, so it understates (a branch that commits no shard has no floor) and can only fire on the branch's own admission. Folding a prior head into the VERDICT is deliberate: if it only reported, dropping the commits would still buy the budget back. The readings that are facts about the evidence rather than breaches of the budget — the two chains disagreeing, shards recording no round, and the rewrite report itself — are printed at exit 0 on their own. The head is the PULL REQUEST's, from the Actions event, never a bare `rev-parse HEAD`: on a `pull_request` event that is the merge ref whose FIRST parent is the base tip, and the shard walk is first-parent, so a bare HEAD read a committed floor of 0 for every PR and this gate could not fire where it runs (an explicit `--head` still wins). The CLOSURE round is exempt by its own `closure_verification` artifact and never by arithmetic on the number: `graph.yaml` `review.closure` declares that round past the cap on purpose, and the exemption is one SHARD's, so a genuine round 3 committed beside a closure shard is still refused. The cap comes from `graph.yaml` `review.cap`, then `repo.yaml` `repair.budget` (the cap's one source, which `graph validate` already holds equal), never re-typed by the caller; `--cap N` overrides both; a graph.yaml DECLARING a `review` block that does not resolve is exit 2 for `warden ship`'s reason — the repo claims a crew, so the question applies and warden cannot answer it — while a repo declaring no cap at all enforces none and SAYS so at exit 0. `--prior-head SHA` (repeatable) is a head this change pushed EARLIER, from outside the branch's current history: its own `base..SHA` is counted with the same derivation and can only RAISE the floor, so a `rebase --onto` that drops the commits which ADDED the shards no longer resets the count in silence and the drop is reported, naming both readings. CI passes the PR's previous head (`github.event.before`, the PRE-rewrite head on a force-push); a head that does not resolve is exit 2, never skipped, since skipping it would return the blind count under the one flag whose purpose is not to be blind. Two limits of that CI witness are OPEN and tracked, not claimed closed, and they do not report alike: the forge sends `before` on the `synchronize` activity type alone — a state the step SEES, so it raises a `::warning::` naming the missing witness and falls back to the in-range count — while `before` is also one push deep, and a `before` that is present, fetchable and itself already rewritten is indistinguishable from a witness that agrees, so the second push after a drop is SILENT | — |
| `round classify` | the repair stop condition, computed rather than argued. Takes the attestation payload (`--findings`, the same file `attest write` reads) and every round directory of the change (`--round`, repeated, any order — the chain is proved by ancestry, never by a clock) and classifies each OPEN finding: `original` (a file the first round's `base_sha...head_sha` changed), `repair` (a file the repair COMMITS themselves wrote — each non-merge first-parent commit from the first head to the latest, so a mid-repair merge COMMIT of the base branch adds nothing; but base-branch work that arrives by fast-forward, squash or cherry-pick IS on that chain, so two subtractions follow. The REACHABILITY subtraction drops every candidate commit reachable from a recorded base, or from the base's NAME resolved now, as the base branch's own — unless it descends from the first round's head, because a base that has absorbed this branch would otherwise drop the repair's own commits. The FILE subtraction drops every path the base branch moved — from the FIRST round's recorded base to each later recorded base, and to the resolved base ref where that ref has not absorbed the branch — but only where the branch carries bytes the base branch itself put there; a base move the branch never merged keeps the path; measured on the absorb fixture in `tests/test_repair_stop.py`, the `squash main` commit is non-merge, first-parent and inside the range, and its `doc.md` still lands in `original`), `both` (in both ranges — read as repair-written, the measurement's own definition, but reported as `both` so a repair that rewrote the whole change is visible). A finding with no file, or on a file in neither range, is `original`: the unclassifiable case never triggers the early stop, and a severity the schema does not name ranks above LOW. Exit `0` when the review loop ends — `clean` (no open finding that counts) or `scaffolding-stop` (every open finding LOW and repair-written); exit `1` when the round `counts` against the cap; exit `2` when a round is unminted, a `--round` path is not a directory (it would otherwise resolve to its PARENT's `round.json` and read as a valid round), its head is not a descendant of the previous, any round's sha does not resolve, the payload cannot be read, the payload's findings declare a round HIGHER than the number of round directories passed (a round that was never minted is invisible here, and its repair commit would be measured as part of the original diff), a finding states a `round` warden cannot read as a whole number at or above 1 (`2.0`, `"2"`, `0`), or the RECORDED BASES DO NOT ADVANCE — a later round naming a base that is not a descendant of the first round's, against which the file subtraction is a silent no-op — never folded into a verdict; the list of exit-2 causes is OPEN, not closed. The report names the original range at COMMIT granularity as well as by file. It also RECORDS its verdict: `classify.json` in the round it classified, carrying the verdict, the exit code, both ends of the chain, `open_findings` (the count of open findings that count), `wording_findings` (the open wording findings that do not), the `rules_version` of the rules read, `rule_kinds` (the kind resolved for each rule id the findings name) and a digest of the findings payload it read, so a claimed scaffolding stop can be checked against the findings the checker actually had. Writes no run dir. Only COUNTING findings are classified: an open finding whose rule declares `judges: wording`, at a severity below every entry in `review.blocking_severities`, is listed separately and never makes the verdict `counts`; a wording finding that does not rank below every blocking severity, a behaviour rule's finding, and an unresolvable rule_id all count. An `unmapped:<slug>` finding names no rule to say what it judges, so it is wording when its `judges` field is absent or says `wording` and behaviour on any other value (`behaviour` is what a reviewer writes; a value the schema would refuse still counts here, because classify validates no schema); a declared rule's finding is what the rule's `judges:` says whatever the record carries. Every input that decides a finding's kind is read AT THE ROUND HEAD — the `head_sha` in the latest `--round`'s `round.json` — never off the working tree, so an uncommitted edit to them changes no verdict: repo.yaml's `review.rules_dir` and `review.blocking_severities`, and each rule's `judges:`. The recorded `rules_version` hashes the repo's surfaces at the head (the rule files, the `checkers` dir beside them, repo.yaml's `review:` subtree) and the platform's two from the RUNNING warden package (the findings schema and `warden/mechanical.py`), so an edit to either of those moves it. The reads are git objects read into memory; no file is written. A repo enrolled below the git root is read through its prefix (`<head>:<prefix>repo.yaml`, and the rules dir resolved against that prefix). Exit 2 when repo.yaml is not committed at the head or does not validate, when `review.rules_dir` resolves outside the repository, when a path it reads (repo.yaml, the rules dir, the `checkers` dir beside it) lies in a git submodule — the path itself or one of its own parent folders is a gitlink at the head, and that submodule is named; a submodule beside the path refuses nothing — and when a ruleset does not load. An absolute `review.rules_dir` is resolved on disk only up to where it enters the repository and at the head from there, so an uncommitted retarget of an in-repo symlink changes no verdict. A committed symlink (a rule file, the rules dir, repo.yaml) is FOLLOWED when its target lies inside the repository's tree at the head, as the working-tree loader follows it on disk; one whose target leaves the repository, does not exist or loops is exit 2 naming it. `classify.json` records that `rules_version` and the resolved `rule_kinds`, so the ruleset a verdict was computed under stays visible and is bound to a commit. | `classify.json` in the latest `--round` directory |
| `attest write/show` | `attest write` files the pre-PR review attestation into a run dir. It REFUSES a `rule_id` that resolves to neither a declared rule nor a well-formed `unmapped:` defect class, a `clean` verdict with a finding still confirmed, an unexpected payload key, or a dirty tree. With `--review-dir <round dir>` it also refuses a roster it can DISPROVE, in BOTH directions: a reviewer claiming `returned: true` with no distinct non-empty regular output file there, an `output` that is a symlink or not a plain basename, two reviewers resolving to one file, an entry it cannot evaluate at all (not an object, no `returned`, a non-boolean `returned`, no `findings` count), a roster in which nobody returned, AND a report left in the directory that no roster entry claims — the dropped reviewer. It also refuses a `--review-dir` that is empty as a path, missing, not a directory, or unlistable, rather than downgrading to unverified: a caller that asked for the check and silently did not get it is the fail-open shape. Without `--review-dir` it does not refuse on the roster or on the round-2 chain rule, which is asked only where a round dir was offered — WITH ONE CARVE-OUT: a roster that is exactly the declared LIGHT crew is refused (exit 2) without the flag too, because the light tier's inertness proof moved out of the `--review-dir` branch, and a tier whose whole premise is that eligibility is recomputed must not be reachable by leaving an argument off; the run manifest records `chain_verification: no-review-dir` so the unasked question is distinguishable from a passed one. THE BASE IT STAMPS is the round's, not the flag's: when `--review-dir` names a round `warden round new` minted for THIS head, `base_sha` is taken from that round's `round.json` — warden's own record of the range its reviewers were shown, which nothing that happens to a ref afterwards can move — and `--base` is what gets stamped only where no such round is offered. `round new --base origin/main` resolves that name once; re-resolving it at write time, hours later, stamped a base that had moved, and a shard that reached main declared a range of 10 files where the round it attests had 5. Where the round's base and `--base` now resolve differently the ROUND's is stamped, and the run manifest records `base_binding` as `round-base-differs` with a `base_binding_detail` naming both shas and the name the round recorded — warden measures only that the two differ, so a moved ref, a different ref name and an annotated tag peeling to its commit all read alike. The other states (`round`, `named`, `no-round`, `round-unreadable`, `round-base-unresolvable`) are tabled in Gate-Pipeline.md's base-binding section. It never refuses on this reading: a round minted for another head, or one warden cannot read, falls back to `--base` here and is refused by the round binding inside `build`, with the roster's message first when both would fire. Every non-refusing reading rides the run manifest — `range_binding`, `patch_binding` (`recorded | empty-range | unavailable`: whether the per-commit patch-ids a content-preserving rebase is matched by were computed), `base_binding` with `base_binding_detail`, `base_ancestry`, `round_binding`, `carry_forward` with `carry_forward_detail`, `chain_verification`, `roster_verification`, and, on a closure round only, `closure_verification` — and that section says which of them also ride the attestation and the committed shard. It stamps `roster_verification: unverified-roster`, which rides into the committed shard, so the corpus distinguishes a checked roster from an asserted one; `round_binding` and `base_ancestry` ride beside it on the same contract — always stamped, absent never read as a pass, and the reading in the committed corpus rather than only on stderr (Gate-Pipeline.md's marker table) forever. `verified` means the claim was backed by an artifact that existed at attest time; it does NOT mean a reviewer ran. It WARNS on stderr, **without refusing**, when the findings name no file the attested range changed — the shape a stale findings file takes — and records that reading as `range_binding: ok \| out-of-range \| empty-range` in the run manifest, which is where the signal ENDS: it never reaches the committed corpus, so `memory stats` and the retro cannot count how often it fires. It also BINDS the round to the commit: when warden minted the review dir, the round's `head_sha` must equal the attested head or the write is REFUSED — an identity check, where `range_binding` is a heuristic that goes silent whenever the colliding branches overlap. A review dir warden did not mint is stamped `round_binding: unminted` in the attestation itself, and `no-review-dir` when none was offered — one of the three states rides into every artifact. Unlike `range_binding`'s reading, this one does NOT stop at stderr and the gitignored run manifest: `memory ingest` carries it into the committed shard and `attest show` prints it, so a later reader of the shards can tell a warden-minted round from any directory handed to `--review-dir`. A DISPROVEN binding is never a recorded state — that refuses the write. Under `--review-dir` it also REFUSES a roster `role` outside the lens vocabulary (the schema's `$defs.lens`: `code-reviewer`, `cross-examiner`, `scoped-re-reviewer`, `builder`, or `crew:<slug>` for a charter lens), a roster entry with no `round`, a finding with no `lens` or `round`, and a finding attributed to a lens no roster entry declares, to a reviewer that did not return, or to a round that lens was not dispatched in. Without `--review-dir` those fields are optional — the committed corpus predates them — but a volunteered `lens` is still joined to the roster. `memory ingest` carries `lens` and `round` onto records and `memory stats` tallies outcome per lens and per round, counting unattributed records apart. It also hashes every claimed report and REFUSES one byte-identical to a report in any sibling round under the rounds root, or to another report claimed in the same round — a reviewer output carried forward is a distinct non-empty file and satisfied the roster check while representing no work; the reading rides in the run manifest as `carry_forward`, never in the artifact. A round never survives a post-review commit; the re-mint cost was measured and accepted. Under `--review-dir` it also STAMPS each roster entry's `outcome` — `reviewed-findings` when findings were counted, `reviewed-clean` only when a zero-finding output names at least one file the range changed, `no-review` when the reviewer did not return or its output names none: a refusal, a classifier decline or a truncated run is a distinct non-empty file and used to read as a clean dispatch. A declared `reviewed-clean` the output cannot corroborate is REFUSED, a declaration the derivation contradicts is refused, and a declared `no-review` always stands (the builder may lower an outcome, never raise it). Without `--review-dir` a declared value is carried as the builder's word and an undeclared one stays absent — absent is UNKNOWN, and `memory stats` never upgrades it. When `graph.yaml` declares a `review` block, under `--review-dir` it also REFUSES a roster whose roles for a round are not exactly that round's declared crew (`warden graph crew --round N`), naming each missing and each extra role; with no `review` block the roster is not compared. The round LABELS are checked as well, against the number `warden round new` minted into `round.json`: the roster's highest round must BE that number — lower and the round being attested was reviewed by nobody, higher and the roster claims a round warden never minted — and a review dir carrying no minted number is REFUSED rather than skipped, so a first and only review can no longer label itself `round: 2` and be held to that round's shorter crew. What that buys is that a shard ingest would have REFUSED to mint does not clear the stop. A bare new rule file with no artifact beside it is **not** in the carve-out: adding a rule bumps `rules_version`, and the tree it produces would fail certification S-05. A rule change's rule-to-artifact link is looked up in the whole committed diff on BOTH arms, so a `forbidden_paths` regex covering only one of the two paths still clears it, on the adoption arm and the pause arm alike. A PROBLEM is still only ever reported for a path the caller handed over. Decided by SHAPE from the **committed** diff (a paused rule file is re-derived from its base bytes and must match exactly), judged against the **committed** `repo.yaml`, never by a marker a session could write. It verifies shape, not permission: it does not re-derive the refutation streak or the ceiling guard. Exit 0 inside, 1 outside naming each reason, 2 could not evaluate. ## `certify --goal`

`warden certify --goal [--ledger PATH] [--report-only]` prints the redesign's
five success criteria as one fixed-width table — one row per item, a verdict
of `PASS`, `FAIL` or `UNMEASURED`, and one evidence line naming the file or
number the verdict was read from — then `GOAL: k of 5`. It is the only
definition of done for those criteria: a closed tracker item is not evidence
here, and nothing in it reads prose.

| Item | Reads | PASS when |
|---|---|---|
| `enrollment` | `.warden/memory/decide/*.json`, else `.github/workflows/ci.yml` and the README's `## Try it` block | a decision shard's `scope` begins with the token `goal:enrollment` (trailing `,` `:` `;` `.` on the token allowed) — the founder's record of an invited collaborator's run URL, reported `collaborator:`; a ruling that merely mentions the literal inside its prose is not the record. Without one, a CI job with a step that invokes `scripts/init-proof.sh` (the block, on fresh repositories) as a gate — the script is the command on one of the step's logical lines, not a mention of the path; nothing after it swallows its exit status (the forms E-01 reads, plus a `&&` list or a lone `&`); no `continue-on-error` that is not literally false and no literally false `if` on the job or step; the script exists in the tree; whether the job runs on every trigger is not read — while the block's `warden certify --level N` line asks N ≥ 2 is reported `mechanics:` — the proof that the commands work, which is not yet a collaborator's run. UNMEASURED when neither exists, naming the scope to record and what the workflow or block lacks |
| `one-round` | `.warden/memory/attest/*.json` | of the 20 most recent attested branches (shards sharing a `bead`, a `pr` or any `range_patch_ids` entry are one branch, so a rebase or merge-forward between rounds does not split it; `base_sha` keys only a shard carrying none of those), the fraction whose highest review `round` is 1 is at least 0.70; the fraction is printed. UNMEASURED below 5 branches; a branch none of whose shards carries a round number is left out and counted in the note |
| `roster` | the newest attest shard — newest by file name, which begins with the shard's timestamp, so an unreadable shard still counts as newest | its `roster_verification` is `verified`. FAIL names the value found, `absent`, or the newest shard's file when it could not be read as a JSON object; an unreadable older shard is named beside a PASS |
| `memory` | `.github/workflows/memory-watch.yml` and `.warden/memory/backtests/*.json` | the workflow exists AND one artifact records `action: adopt` — the file `warden autonomy adopt` writes. FAIL names whichever half is missing |
| `cage` | `--ledger PATH`, the cage's `ledger.csv` | at least 10 rows whose outcome is `done` and whose PR column is non-empty, printed as `n/10`. UNMEASURED without `--ledger` |

Exit 0 only when all five are PASS; `--report-only` exits 0 whatever the
table says, which is how this repository's CI posts the table into every PR's
job summary without making it a gate. The ladder's `--level` and
`--capability` do not combine with `--goal`, and `--ledger` / `--report-only`
apply to `--goal` only: a mix exits 2 rather than ignoring a flag. The run
dir carries the same verdicts as `goal.json`.
